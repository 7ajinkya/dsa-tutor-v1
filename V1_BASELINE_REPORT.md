## 4. V0 architecture findings (instruction §4A)

Strictly one-way dependencies (verified by import inspection):
`CLI (app/interactive.py, cli.py) → Application (app/service.py) → { Learning engine (domain/*), AI (ai/*), Persistence (persistence/*) }` — domain depends on nothing above it.

**Domain layer — the learning engine (owns all pedagogy):**
- `models.py` — shared vocabulary: `Skill` (with `evidence_requirements`, `module`, `is_boundary`, `is_optional`, descriptive 4-axis `complexity`), `LearningUnit` (teach/practice/assess/apply; teach units carry theory text), `Exercise` = Learning Activity (`role` = evidence type demonstrated, `scope` micro/problem, `required_capabilities` for the readiness gate, `hint_ladder`, `source` curated/ai), `Attempt`, `EvidenceRecord`, `SkillAssessment` (numeric, analytics-only), `LearnerState` (exact resume point: skill/unit/exercise, pending action, completed units, per-exercise failure counts, difficulty shift), `EngineDecision` (action + skill/unit/exercise + human-readable `why` chain), `MasteryState` (NOT_SEEN→INTRODUCED→DEVELOPING→PRACTICED→PROFICIENT→INDEPENDENT), 13 session event types.
- `engine.py` — pure and deterministic: no I/O, never calls the AI. `select_next()` walks the topological `learning_order()`, skips mastered/PRACTICED+ skills (evidence-based placement bypass), serves optional skills only after all core skills, redirects to `PREREQUISITE_REVISIT` when core prereqs lack evidence. `decide_after_attempt()` implements the struggle ladder: 1st failure → `REMEDIATION` (smaller AI-generated micro-question, skill-locked); 2nd → `PREREQUISITE_REVISIT` (AI `missing_skill` must be in the prerequisite closure) or `REPEAT`; ≥3rd → reassessment (trend improving → variation; weak state → `REDUCE_DIFFICULTY`; else cool-down variation) — intervention, never termination. Excellent independent streaks (score ≥ 0.9, no hints) can `INCREASE_DIFFICULTY`. `check_readiness()` gates problem-scope activities on demonstrated *independent* evidence of declared capabilities (30-day recency) and explains deferrals. Every decision carries its `why` chain.
- `mastery.py` — the authority: `derive_state()` uses per-evidence-type predicates only (numbers are analytics). Latest outcome per type wins → mastery is deliberately **non-monotonic**; PROFICIENT/INDEPENDENT require ≥2 independent successes within 30 days; INDEPENDENT additionally requires application/transfer evidence. `outcome_for_attempt()`: assistance L0–L1 = independent, L2–L4 = assisted, L5–L6/solution reveal can never be independent.
- `curriculum.py` — validated graph: acyclicity (Kahn), single boundary skill (`v0_readiness`, nothing may depend on it), coverage (every skill has units + exercises), impossible-skill detection (every required evidence type must have a supporting activity), capability-mapping validation, deterministic `learning_order()`. Verified: `validate()` returns no errors.

**Application layer (`service.py`, 41 KB):** owns transaction boundaries — `storage.record_interaction(attempt, evidence, assessment, state, events)` commits one interaction atomically. Grades MCQs deterministically (`grade_mcq`, provider="deterministic" — zero AI calls); sends everything else to `ai.evaluate()`. Renders `TurnView` DTOs (theory | exercise | ended | info) with decision, evaluation, hint, daily plan, remaining minutes. Also: daily-plan adaptation (yesterday's completion rate adjusts today's unit target 2–8), session plan preview (units, theory blocks, question counts), confidence collection (one per high-complexity skill; drives over/underconfident signals), low-AI-confidence gate (ai_confidence < 0.5 → AI recommendation neutralized + why-note), budget guard (stop at natural boundary when < 5 min remain or budget exhausted), `export_last_session()` markdown transcript.

**AI layer (`ai/`):** exactly five operations (`evaluate`, `detect_misconception`, `generate_hint`, `explain`, `generate_controlled_remediation`) on abstract `AITutor`, with `MockAITutor` for tests. All results are schema-validated *observations* — no field can mutate state; `HintResult.is_solution=true` is rejected at schema level; `missing_skill` must be a real skill id; `recommended_action` is whitelisted; `ai_confidence` is a self-reported safety signal. Providers: `builtin` (offline deterministic: rubric free-form grading, hint ladders per curated exercise, misconception library, output-trace diagnosis, complexity normalization `O(N+M)≡O(V+E)`, AST-guarded subprocess code execution with 5s timeout), `openai` (any OpenAI-compatible endpoint, JSON mode, retries with backoff on 429/5xx, per-session cap), `hybrid` (external first; on ANY failure falls back to builtin, marks `degraded=True`, records `last_fallback_reason`). `UsageGuard` counts every outbound HTTP attempt per calendar day in a local JSON file and refuses external calls past the configured limit (hybrid then silently continues on builtin).

**Persistence:** `MySQLStorage` and `MemoryStorage` implement one identical interface (learner, sessions, events, attempts, evidence, assessments, state, daily plans, `record_interaction`, `ensure_exercise` for AI-generated items, `log_ai_interaction`, `record_hint_event`). `db.py` self-bootstraps: create-database-if-missing, run `schema.sql` statement-by-statement, repair missing columns/indexes (idempotent `setup-db`). Schema: 15 InnoDB tables — `users, topics, skills, skill_prerequisites, learning_units, exercises, daily_plans, sessions, session_events, attempts, assessment_evidence, skill_assessments, ai_interactions, hint_events, learner_state`. Curriculum lives in code and is mirrored to MySQL by `seed.py` (upsert, engine still reads code).

**Curriculum content (verified by import + validate):** 1 topic; **38 skills** in Modules A–F (A Graph Mental Model 9, B Representation 5, C Traversal Fundamentals 5, D BFS 7, E DFS 8, F Integration & Application 4); **67 prerequisite edges**; **62 units** (38 teach — all with theory text, 22 practice, 1 apply, 1 assess); **75 exercises** (50 mcq, 6 output_prediction, 6 free_form, 4 code_tracing, 4 code_writing, 4 complexity_question, 1 graph_construction), 71 micro + **4 problem-scope** (`e049_bfs_implementation`, `e055_dfs_implementation`, `e060_traversal_application`, `e062_v0_readiness`), all curated (`source=curated`); boundary `v0_readiness`; optional `explicit_stack_dfs`.

## 5. V0 execution flow (instruction §4B)

1. **Learner starts session** — `cli.py cmd_start` → `_build_service` (MySQL healthcheck + schema gate, or `--offline` MemoryStorage) → `TutorService.start_session()`: validates config, loads/creates today's `DailyPlan`, creates/resumes `TutoringSession`, appends `SESSION_STARTED` event.
2. **Engine selects activity** — `engine.select_next(snapshot)` (state + assessments + evidence + session + remaining minutes) → `EngineDecision` (ADVANCE/PREREQUISITE_REVISIT/…+ why).
3. **Activity presented** — service resolves the exercise (curated or previously generated), saves resume point into `LearnerState`, emits `QUESTION_PRESENTED`; teach units render theory first with a read-gate ("then N quick checks"), then the unit's exercises in order; CLI shows skill::type, position "k of n in this unit", last why-reason; optional confidence prompt.
4. **Learner responds** — free text / MCQ letter / multiline code terminated by `END`; in-session commands `hint | why | explain | progress | solution | stop` (hint walks L1→L5, L6 gated reveal; every hint event persisted).
5. **Evaluation** — MCQ: deterministic local grading; others: `ai.evaluate()` (builtin rubric/trace/AST-test grading or external LLM with schema validation). Confidence signal computed vs reported confidence.
6. **Evidence** — `mastery.evidence_for_attempt()` → typed `EvidenceRecord`s (evidence type = exercise role; dimension weights from `DIMENSION_AFFINITY`; outcome from correctness + assistance level); `SkillAssessment` recomputed from the full evidence stream; assistance level recorded on attempt (`max_assistance_level`).
7. **Learner state / progression** — `engine.decide_after_attempt()` on a snapshot that *includes the just-produced evidence* (never stale) → next action; unit completion bookkeeping; struggle ladder / mastery advance / readiness gate as in §4.
8. **Persistence (one transaction)** — attempt + evidence + assessment + state + events commit together or roll back; then the loop repeats from 3 with the chosen next activity.
9. **Session end** — budget guard, natural completion ("all skills mastered"), or learner `stop`/Ctrl+C → session `paused`/`completed` with exact resume point; `--resume` continues from the persisted exercise.

## 6. Existing extension points (instruction §4C)

- **HTTP/API layer (thin):** `TutorService` already exposes use-case methods returning DTOs (`TurnView`, plan dict, progress dict) with no CLI/console coupling. A thin FastAPI (or stdlib http) layer can wrap 1:1: `start`, `plan`, `theory-seen`, `answer`, `hint`, `solution`, `explain`, `why`, `progress`, `confidence`, `stop`, `resume`. No engine changes needed.
- **Vue frontend:** rendering is already isolated in `app/interactive.py` ("renders; it never decides"). The frontend consumes the same `TurnView` data; `EngineDecision.why` gives per-step explanations; `session_plan()` gives orientation data (units, question counts, theory blocks); `unit_position` gives progress-in-unit.
- **Storage swap:** `MemoryStorage`/`MySQLStorage` share one interface — an API server picks MySQL while tests keep MemoryStorage; no engine coupling.
- **AI improvements:** provider factory + 5-operation interface + `MockAITutor`; adding an LLM is one env var (`AI_PROVIDER=hybrid`), and hybrid fallback is already proven (§9 demo 3).
- **Improved sequencing:** progression is entirely inside `engine.select_next`/`decide_after_attempt`; per-unit activity sequences already exist as data (`exercises_for_unit` ordering, unit types teach/practice/assess/apply). Instruction §7's "sequence is authoritative, not THEORY→MCQ→PROBLEM" is already satisfied by data; UI/API just must render it.
- **Observability:** every decision (`why`), event (13 types), AI call (`ai_interactions` with latency/provider/prompt_version), and hint (`hint_events`) is already persisted — a learner-facing "why" view or an operator dashboard can be built on existing tables with zero engine changes.

## 7. Current limitations relevant to V1 (instruction §4D)

Engine/data limitations (V1-relevant):
1. **CLI orientation is informative but shallow.** Audit against the instruction's seven learner questions:
   - *What am I doing?* — covered (skill::type header, "exercise k of n in unit", STUDY title).
   - *Why am I doing it?* — **partial**: only the last `why` reason is shown inline; the full chain requires typing `why`.
   - *Diagnostic or instructional?* — **not communicated**: unit type (teach/practice/assess/apply), placement-bypass, and readiness-gate deferrals are not surfaced as a label.
   - *How many activities/questions?* — **partial**: the session plan lists unit/question counts, but it is a static preview — remediations/variations change it and the delta is not announced.
   - *What is expected from me?* — **partial**: answer-format help exists per type, but no "this checks X capability" framing.
   - *What happens next?* — **partial**: theory blocks announce their question count; post-answer transitions show a one-line reason, no preview.
   - *How much remains?* — **partial**: budget/remaining minutes only in the plan header; no in-session progress ticker; "k of n in unit" is the only granular indicator.
   - *Why remediation/progression?* — the engine's why-chain explains it and is persisted, but the CLI surfaces one line by default.
2. **Console-only experience**: no session-orientation screen, no resume-orientation ("here is where you stopped and why"), no visual progress/state view beyond the text `progress` table.
3. **Offline mode is non-persistent** (documented): `--offline` demo state dies with the process; persistence requires MySQL.
4. **Single hardcoded learner** (`local_learner`), no auth — fine for local V1, blocks any multi-user plan later.
5. **Code runner is process isolation, not a sandbox** (honestly documented in `code_runner.py`); local single-user only.
6. **Builtin free-form grading is keyword-rubric based** — quality ceiling without an external LLM (hybrid solves it, optional).
7. **Fixed constants**: 30-day mastery recency, budget midpoints (12/25/45), hint ladder depth — not learner-tuned.
8. **Unbounded growth**: `session_events`, `ai_interactions`, `logs/`, `exports/` — fine single-user, revisit with the API/UI.
9. **Documentation drift**: README §7 says "63 tests" and §9 "67"; REVISION_PLAN says "76/90" — the actual suite is **95 collected**. (V0 is frozen; v1 should correct its docs in the first implementation slice, not in this baseline.)
